# 渠道并发实时状态可视化与运维策略完整迁移

## Problem Statement

`tokendazi_op` 已经具备渠道并发限制的核心字段、基础槽位控制、等待与并发冷却能力，也能在渠道编辑抽屉中配置渠道并发上限；但管理员目前无法在渠道列表中看到渠道并发快照，无法从列表直接调整渠道并发上限，也没有一个完整、可见的渠道并发策略面板。当前实现还存在以下缺口：

- 缺少面向渠道列表的实时渠道并发快照接口与前端轮询链路，管理员无法判断受限渠道当前是空闲、占用、饱和、排队还是处于并发冷却。
- 当前只有 7 项渠道并发策略参数；固定对齐基线中的 HTTP 429 冷却开关、模糊消息冷却开关、负载快照缓存开关、缓存 TTL 和最大抢占次数尚未完整进入当前运行时。
- 当前负载读取会随候选渠道数量和请求量放大 Redis 压力，缺少负载快照缓存、singleflight 合并、Redis 分批读取、共享抓取上限和每轮抢占预算。
- 当前模糊错误关键词会直接触发并发冷却，无法按二开最新版默认行为将明确的 HTTP 429 与容易误判的模糊消息匹配分开控制。
- 当前渠道更新会受零值更新语义影响，明确提交 `max_concurrency = 0` 时可能无法清除渠道并发上限。
- 二开最新版使用宽泛的管理员认证且前端目录结构与当前 Base 不同，不能整段复制；迁移必须保留当前 Base 的细粒度渠道权限、统一前端、现有渠道表格能力和更新后的错误处理约束。

管理员需要在现有渠道管理和系统运维设置中获得完整、可控、低开销的实时状态体验，同时不得把渠道并发快照误解为历史监控、渠道健康结论或可消费的并发配额。

## Solution

以固定基线 `refs/remotes/solve/main@762ce21c4` 为功能参考，在当前 `tokendazi_op` 架构中完整迁移两部分能力：

1. 在现有渠道列表增加渠道并发上限展示：桌面表格增加列，当前 Base 默认启用的桌面卡片视图复用同一状态与编辑能力；为当前页受限渠道立即获取并每 10 秒刷新渠道并发快照，显示 `active/max`、等待数量和 `Cooling` 状态，并提供受 `ChannelWrite` 权限控制的行内渠道并发上限编辑。移动端不显示该能力。
2. 在“系统设置 → 运维”增加“渠道并发限制”面板，将 12 项渠道并发策略全部可视化，按常用策略和高级运行参数分组，并通过现有 Root 专属 Option 能力逐项保存实际发生变化的值。

迁移同时补齐二开最新版的运行时抗压能力：负载快照缓存、相同候选集读取合并、Redis 分批读取、抓取并发保护、一次新鲜快照确认、原子等待登记、抖动指数退避、并发冷却触发开关和每轮最大抢占次数。负载快照缓存为候选渠道排序和管理侧瞬时状态读取提供观察结果；Redis 原子槽位获取始终是并发正确性的权威判定点。

本功能保留当前 Base 的权限边界：`ChannelRead` 查看渠道并发快照，`ChannelWrite` 修改单条渠道并发上限，Root 修改全局渠道并发策略。刷新失败时不打扰管理员：首次失败显示不可用占位，后续失败保留该查询集合最后一次成功的渠道并发快照。当前项目尚未正式上线，因此缺失的新配置直接采用二开最新版默认值，不增加旧版识别、回填或兼容迁移分支。

## User Stories

1. 作为拥有 `ChannelRead` 权限的管理员，我希望在桌面端渠道列表的表格或卡片视图看到渠道并发上限，从而无需切换视图或打开单条渠道详情即可了解其限制和瞬时状态。
2. 作为拥有 `ChannelRead` 权限的管理员，我希望受限渠道以 `active/max` 显示活跃请求数与渠道并发上限，从而快速判断当前容量使用情况。
3. 作为拥有 `ChannelRead` 权限的管理员，我希望仅在等待请求数大于零时看到 `+N`，从而区分正在执行的请求与正在排队的请求。
4. 作为拥有 `ChannelRead` 权限的管理员，我希望处于并发冷却的渠道额外显示蓝色 `Cooling` 标记，从而知道该渠道正在短期退避而不是被永久禁用。
5. 作为拥有 `ChannelRead` 权限的管理员，我希望活跃数为零、未饱和但已有活跃请求、达到或超过上限时分别使用灰色、黄色和红色状态，从而一眼识别压力等级。
6. 作为拥有 `ChannelRead` 权限的管理员，我希望进入渠道列表后立即获取当前页渠道并发快照，从而不必等待第一个轮询周期。
7. 作为拥有 `ChannelRead` 权限的管理员，我希望页面可见时每 10 秒刷新一次渠道并发快照，从而持续看到足够及时且不会过度施压的状态。
8. 作为平台运维人员，我希望轮询只请求当前页中渠道并发上限大于零的渠道，从而避免为不可见渠道产生额外数据库和 Redis 读取。
9. 作为平台运维人员，我希望切换分页、筛选、搜索、排序或标签模式后只查询新页面对应的受限渠道，从而保证状态与当前视图一致。
10. 作为使用标签模式的管理员，我希望展开后的真实子渠道可以获得各自渠道并发快照，而标签汇总行本身不伪造聚合快照，从而避免把不同渠道的状态错误合并。
11. 作为平台运维人员，我希望当前页不存在受限渠道时完全停用渠道并发快照请求，从而让无限制渠道保持零额外读取路径。
12. 作为查看无限制渠道的管理员，我希望其不显示虚构的 `0/0` 渠道并发快照，从而明确它未参与渠道并发限制。
13. 作为查看标签汇总行的管理员，我希望渠道并发上限列显示 `-` 且不可编辑，从而明确汇总行不是一条真实渠道。
14. 作为管理员，我希望某个受限渠道在首次渠道并发快照获取失败时显示 `-`，从而不会把未知状态误报为零负载。
15. 作为管理员，我希望后续轮询发生网络错误、HTTP 错误或业务失败时继续看到该查询集合最后一次成功的渠道并发快照，从而避免状态闪烁或被错误清空。
16. 作为管理员，我希望后台轮询失败保持静默，不出现每 10 秒重复 toast，从而不让短暂故障干扰正常运维操作。
17. 作为管理员，我希望浏览器标签页进入后台时暂停 10 秒轮询，并在恢复可见后继续刷新，从而减少无意义请求。
18. 作为管理员，我希望不同页面或不同受限渠道集合各自管理最后成功快照，从而不会把上一页渠道的旧状态显示到当前页。
19. 作为移动端管理员，我希望渠道并发上限列在移动布局中隐藏，从而保持渠道卡片紧凑且不挤压核心操作。
20. 作为桌面端管理员，我希望渠道并发上限列默认可见并仍服从现有列显示偏好，从而既获得新状态也保留表格个性化能力。
21. 作为拥有 `ChannelRead` 权限但没有 `ChannelWrite` 权限的管理员，我希望能查看渠道并发快照但看不到可执行的行内编辑控件，从而遵守最小权限原则。
22. 作为不拥有 `ChannelRead` 权限的主体，我希望服务端拒绝渠道并发快照请求，从而不能通过直接调用接口绕过渠道读取权限。
23. 作为拥有 `ChannelWrite` 权限的管理员，我希望在渠道表格中使用现有风格的数字控件修改单条渠道并发上限，从而快速完成日常容量调整。
24. 作为拥有 `ChannelWrite` 权限的管理员，我希望输入正整数时设置新的渠道并发上限，从而让后续请求受该上限约束。
25. 作为拥有 `ChannelWrite` 权限的管理员，我希望明确输入 `0` 时清除渠道并发上限，从而让该渠道恢复为无限制渠道。
26. 作为渠道管理员，我希望更新请求未包含 `max_concurrency` 时保持原值，从而让编辑其他字段不会意外改变渠道并发上限。
27. 作为渠道管理员，我希望更新请求将 `max_concurrency` 设为 `null` 时按未提供处理，从而兼容部分更新语义并保留原值。
28. 作为渠道管理员，我希望负数渠道并发上限被服务端拒绝且原值不变，从而避免无意义或危险的配置进入运行时。
29. 作为渠道管理员，我希望新增渠道和更新渠道使用一致的非负校验，从而不会通过不同入口写入无效渠道并发上限。
30. 作为渠道管理员，我希望渠道编辑抽屉与表格行内编辑遵守相同的正数设置、`0` 清除、缺失保持和负数拒绝语义，从而避免入口之间行为不一致。
31. 作为拥有 `ChannelWrite` 权限的管理员，我希望行内更新成功后渠道列表与轮询目标随新值刷新，从而让设置为正数的渠道开始显示快照、清零的渠道停止轮询。
32. 作为权限不足的管理员，我希望即使手工构造渠道更新请求也被服务端权限检查拒绝，从而使前端隐藏控件不成为唯一防线。
33. 作为渠道管理员，我希望本功能不增加批量渠道并发上限编辑，从而不扩大现有批量接口的职责或干扰其专用能力。
34. 作为 Root 管理员，我希望在“系统设置 → 运维”中找到“渠道并发限制”面板，从而集中管理所有渠道共用的等待、并发冷却和负载读取策略。
35. 作为 Root 管理员，我希望面板同时显示全部 12 项渠道并发策略，从而不需要通过隐藏配置修改高级运行参数。
36. 作为 Root 管理员，我希望 8 项日常开关和策略放在“常用策略”，4 项底层参数放在“高级运行参数”，从而在完整可见的同时保持信息层级清晰。
37. 作为 Root 管理员，我希望未设置值时看到并使用二开最新版默认值，从而在尚未上线的环境中直接获得已确认的推荐行为。
38. 作为 Root 管理员，我希望默认开启“并发满时等待”，从而让受限渠道短暂饱和时可以等待槽位而不是立即失败。
39. 作为 Root 管理员，我希望关闭等待后，等待超时、单渠道最大等待数和等待轮询间隔输入被禁用但保留原值，从而重新开启时恢复之前配置。
40. 作为 Root 管理员，我希望配置等待超时，从而限制单个请求为渠道槽位等待的最长时间。
41. 作为 Root 管理员，我希望将单渠道最大等待数设为 `0` 时明确表示自动跟随该渠道的渠道并发上限，从而减少逐渠道重复配置。
42. 作为 Root 管理员，我希望配置等待轮询间隔，从而控制等待请求重新尝试权威槽位获取的基础节奏。
43. 作为 Root 管理员，我希望配置槽位 TTL，从而为异常中断或未释放租约提供最终自动回收边界。
44. 作为 Root 管理员，我希望默认开启并发冷却，从而让触发已配置上游限流条件的渠道短期退出调度。
45. 作为 Root 管理员，我希望关闭并发冷却后，冷却时长和两个触发条件输入被禁用但保留原值，从而重新开启时恢复之前配置。
46. 作为 Root 管理员，我希望配置并发冷却时长，从而控制渠道短期退避的持续时间。
47. 作为 Root 管理员，我希望默认开启“上游 HTTP 429 触发并发冷却”，从而对明确限流信号执行可预期的退避。
48. 作为 Root 管理员，我希望“错误消息模糊匹配触发并发冷却”默认关闭且明确提示误判风险，从而避免仅因消息提到 `rate limit`、`overload` 或 `capacity` 就错误冷却渠道。
49. 作为平台运维人员，我希望额度不足、余额不足和配额耗尽类错误即使返回 HTTP 429 也不触发并发冷却，从而不把账户问题误判为瞬时并发压力。
50. 作为 Root 管理员，我希望默认开启负载快照缓存，从而降低相同候选集重复读取 Redis 的压力。
51. 作为 Root 管理员，我希望关闭负载快照缓存后，缓存 TTL 输入被禁用但保留原值，从而可临时切换为实时读取进行排障并能轻松恢复。
52. 作为 Root 管理员，我希望配置负载快照缓存 TTL，从而在 Redis 压力与排序时效之间做有界权衡。
53. 作为 Root 管理员，我希望配置每轮最大抢占次数，从而限制一次渠道选择在全饱和候选集上执行的权威槽位获取次数。
54. 作为 Root 管理员，我希望保存时只提交实际变化的设置并按顺序逐项保存，从而不重写未修改的全局 Option。
55. 作为 Root 管理员，我希望没有变化时得到“无更改可保存”的反馈，从而避免发出无意义请求。
56. 作为 Root 管理员，我希望某一项保存失败时看到失败反馈且界面不宣称全部成功，从而知道顺序保存可能已经持久化失败项之前的部分设置。
57. 作为 Root 管理员，我希望数值输入在提交前遵守运行时支持的整数范围，从而尽早发现非法值而不是依赖静默回退。
58. 作为使用任一现有界面语言的管理员，我希望渠道并发快照、`Cooling`、权限相关状态、设置标签、说明和校验信息都有对应翻译，从而在七种受支持语言中获得一致体验。
59. 作为平台请求调度器，我希望渠道并发上限小于或等于零的渠道不因负载读取或槽位获取访问 Redis，也不消耗抢占预算，从而维持无限制渠道的低开销路由路径。
60. 作为平台请求调度器和管理侧观察者，我希望负载快照缓存只提供排序与状态展示所需的观察结果，从而即使快照短暂陈旧也不会直接放行请求或突破渠道并发上限。
61. 作为平台请求调度器，我希望每次受限渠道选择最终都执行实时、原子的槽位获取，从而由权威状态检查并发冷却与渠道并发上限并登记本请求租约。
62. 作为平台运维人员，我希望相同候选集的并发缓存未命中通过 singleflight 合并，从而流量突增时只产生一次共享负载抓取。
63. 作为平台运维人员，我希望大量候选渠道的 Redis 负载读取按固定大小分批且不截断候选集，从而同时限制单次 pipeline 大小并保留所有回退渠道。
64. 作为平台运维人员，我希望不同候选集的共享 Redis 抓取具有全局并发上限和超时边界，从而 Redis 延迟升高时不会堆积无限后台抓取。
65. 作为平台请求调度器，我希望负载抓取失败时按既有容错规则降级到进程内状态进行排序，而权威 Redis 抢槽失败仍保持失败关闭，从而兼顾可用性与多实例并发正确性。
66. 作为平台请求调度器，我希望缓存中的并发冷却状态过滤掉所有候选渠道时执行一次绕过缓存的新鲜读取，从而让刚结束冷却的渠道无需等待完整缓存窗口即可重新参与选择。
67. 作为平台请求调度器，我希望一次新鲜读取失败时保留原来的过滤结果而不是把确认读取升级成更严重的请求失败，从而让辅助确认不降低主路径可靠性。
68. 作为平台请求调度器，我希望每轮抢占预算耗尽后进入最佳等待候选的既有等待流程，而不是丢弃低优先级候选或无限执行 Redis 脚本，从而保持路由语义并限制成本。
69. 作为平台请求调度器，我希望等待队列容量检查、登记和过期设置原子完成，从而并发突发时等待人数不会越过已配置上限。
70. 作为平台请求调度器，我希望等待重试使用带抖动的指数退避，从而多个实例和请求不会在固定间隔同时冲击 Redis。
71. 作为平台运维人员，我希望一次结果不确定的槽位获取只执行一次有界的后台清理并由槽位 TTL 最终兜底，从而减少幽灵槽且不在 Redis 故障时放大重试压力。
72. 作为后续维护者，我希望负载快照缓存与权威槽位所有权之间的边界有明确规格和 ADR，从而未来重构不会把缓存误用为可消费并发配额。

## Implementation Decisions

1. **固定基线与适配原则。** 功能参考固定为 `refs/remotes/solve/main@762ce21c4`，但不整分支合并，也不照搬其宽泛管理员认证、Classic 前端或 `web/default` 目录结构。实现必须适配当前 Base 的统一前端、细粒度 Casbin 权限、渠道缓存与更新流程、现有表格抽象以及七语国际化体系。
2. **功能边界。** 本次完整交付渠道列表实时渠道并发快照与运维渠道并发策略面板两部分；两者共用同一渠道并发运行时事实，不创建独立监控领域、历史存储或第二套状态来源。
3. **权限契约。** 渠道并发快照接口要求 `ChannelRead`，并声明相同的访问令牌权限；行内渠道并发上限编辑要求 `ChannelWrite`；全局渠道并发策略继续通过 Root 专属 Option 接口读写。前端能力展示与服务端授权必须同时生效。
4. **快照接口。** 增加 `GET /api/channel/concurrency`，使用逗号分隔的 `ids` 查询参数。一次请求最多接受 200 个原始 ID 片段；超过上限返回 HTTP 400。空参数、格式错误、零和负数 ID 被忽略；没有有效 ID 时成功返回空数组。
5. **快照返回。** 接口只返回数据库中存在且渠道并发上限大于零的渠道，每项包含渠道 ID、渠道并发上限、活跃请求数、等待请求数和并发冷却布尔值。未找到渠道和无限制渠道不产生占位项，也不触发其 Redis 状态读取。
6. **轮询集合。** 前端从当前页真实渠道行收集渠道并发上限大于零的 ID，稳定排序并去重；标签模式可以收集当前页聚合行中的真实子渠道，但标签汇总行本身不进入查询。集合为空时关闭查询。
7. **轮询生命周期。** 首次渲染立即请求，此后页面可见时每 10 秒刷新；浏览器页面隐藏时暂停后台刷新。分页、筛选、搜索、排序、标签模式或渠道并发上限变化会产生新的查询集合，不得把其他集合的状态映射到当前集合。
8. **失败语义。** 网络失败、非成功 HTTP 状态和 HTTP 200 中的 `success: false` 都视为刷新失败。首次失败时受限渠道的快照区域显示 `-`；已经有成功结果时，所有失败类型都静默保留该集合最后一次成功结果，不清空、不替换为零、不重复 toast。
9. **状态展示。** 受限渠道显示 `active/max`；等待数大于零时追加 `+N`；并发冷却为真时追加蓝色 `Cooling`。`active = 0` 使用灰色，`0 < active < max` 使用黄色，`active >= max` 使用红色。无限制渠道不显示快照徽标，标签汇总行显示 `-`。
10. **列表交互。** 桌面渠道表新增默认可见、不可排序的渠道并发上限列，并沿用现有列偏好能力；当前 Base 默认启用的桌面卡片视图复用同一状态和编辑组件，避免管理员必须先切换到表格才能使用本功能。移动表格与移动卡片都不显示渠道并发上限。渠道并发快照映射应通过渠道表格已有的特性接口传给单元格，不为本功能绕开或复制通用表格行为。
11. **行内编辑。** 拥有 `ChannelWrite` 的管理员使用与现有渠道数字字段一致的非负整数控件编辑单条渠道并发上限；只读管理员获得相同状态展示但没有可执行编辑控件。成功后刷新渠道列表与相应快照查询目标，失败沿用当前渠道字段更新反馈。
12. **存在性感知更新。** 渠道更新必须区分字段是否出现：正整数写入新上限，显式 `0` 必须持久化并清除上限，缺失或 `null` 保留原值，负数在写入前拒绝且不改变原值。新增渠道同样拒绝负数。该语义适用于行内编辑和现有渠道编辑入口。
13. **不扩展批量编辑。** 不给渠道批量编辑或标签汇总编辑增加渠道并发上限能力，也不改造当前已有的专用批量请求契约。
14. **12 项设置。** 所有设置属于同一个渠道并发策略模块，缺失值直接采用下表默认值；当前环境尚未正式上线，不检测旧安装、不回填历史 Option、不增加兼容模式。

| 分组 | 设置 | Option 字段 | 默认值 | 运行时约束与语义 |
| --- | --- | --- | --- | --- |
| 常用策略 | 并发满时等待 | `wait_enabled` | 开启 | 关闭后不进入等待队列 |
| 常用策略 | 等待超时 | `wait_timeout_ms` | `5000 ms` | 正整数，最大 `60000 ms` |
| 常用策略 | 单渠道最大等待数 | `max_waiting_per_channel` | `0` | `0` 表示自动跟随该渠道并发上限；显式值最大 `10000` |
| 常用策略 | 启用并发冷却 | `cooldown_enabled` | 开启 | 主开关关闭时所有触发条件失效 |
| 常用策略 | 并发冷却时长 | `cooldown_seconds` | `30 s` | 正整数，最大 `3600 s` |
| 常用策略 | HTTP 429 触发并发冷却 | `cooldown_on_status_429` | 开启 | 仅在并发冷却主开关开启时生效 |

| 高级运行参数 | 负载快照缓存 TTL | `load_cache_ttl_ms` | `200 ms` | 正整数，最大 `5000 ms`；缓存关闭时不生效 |

15. **面板布局与依赖状态。** 8 项常用策略和 4 项高级运行参数始终显示。关闭等待时禁用但保留等待超时、单渠道最大等待数和等待轮询间隔；关闭并发冷却时禁用但保留冷却时长与两个触发开关；关闭负载快照缓存时禁用但保留缓存 TTL。槽位 TTL 和每轮最大抢占次数始终可编辑。
16. **设置保存。** 面板复用现有 Root Option 更新能力，对比已加载基线后只保存发生变化的字段，并按稳定顺序逐项等待保存结果。不新增专用原子保存接口，也不把 12 项伪装成一次事务；中途失败时停止后续保存，不回滚此前成功项，也不得显示整体成功。管理员重新加载后以服务端实际值为准。
17. **热更新。** 12 项设置继续通过现有全局配置机制生效，不增加数据库 schema。开关与数值在保存后作用于后续渠道选择、等待、并发冷却和负载读取。
18. **并发冷却触发。** 并发冷却主开关优先；额度不足、配额耗尽、余额不足及对应中英文关键词始终排除。明确 HTTP 429 是否触发由 `cooldown_on_status_429` 控制；非 429 错误只有在 `cooldown_on_message_match` 开启且消息包含既定限流、过载或容量关键词时才触发。
19. **负载快照缓存边界。** 缓存键由有序候选渠道身份和各自渠道并发上限构成，默认 TTL 为 200ms，候选集缓存条目总量有界。路由排序与管理侧状态接口共享这项有界读取预算；返回值使用独立快照，不能共享可变槽位所有权。每个受限请求仍必须实时执行权威槽位获取。
20. **singleflight 与新鲜读取。** 同一候选集的普通缓存未命中合并为一次 Redis 抓取；绕过缓存的新鲜读取使用独立合并键，成功后刷新共享缓存。若缓存中的并发冷却状态过滤全部候选，只执行一次新鲜确认；该确认失败不把辅助读取变成更强的业务失败。
21. **Redis 分批读取。** 有界候选渠道按 ID 稳定排序，以每批最多 50 个渠道读取活跃数、等待数和并发冷却状态；一次抓取只读取一次 Redis 时间。分批只限制单次 pipeline，不截断候选集或改变低优先级回退语义。
22. **共享抓取保护。** 共享 Redis 负载抓取与发起请求的取消解耦，但具有 3 秒总超时和最多 2 个并发抓取槽位；槽位饱和或读取失败时退回既有进程内负载排序。单个等待调用方取消时只停止自身等待，不取消其他调用方共享的抓取。
23. **权威槽位获取。** Redis 开启时，实时槽位获取在同一个原子操作中检查并发冷却、清理过期槽位、检查渠道并发上限并登记或续租请求槽位；负载快照永远不能替代该操作。Redis 权威获取报错时保持失败关闭，不跨实例退化为可能超卖的本地获取。
24. **等待与退避。** 等待队列的容量检查、计数增加和过期时间设置必须原子完成。等待重试从配置的基础间隔开始，在 `[interval/2, interval)` 范围内抖动并指数增长；退避上限为 `max(基础间隔, min(基础间隔 × 8, 1 秒))`，最终受等待超时约束。
25. **抢占预算。** 每次渠道选择过程共享一个最大抢占次数预算，普通排序与有 readiness 排名的路径都必须遵守。只有渠道并发上限大于零的候选消耗预算；预算耗尽后保留最佳等待候选并进入既有等待流程，不截断候选查询，也不改变无限制渠道行为。
26. **不确定获取清理。** Redis 客户端看到错误但服务端可能已完成槽位登记时，发起一次与请求上下文分离、最长 500ms 的尽力清理；不重试清理，最终由槽位 TTL 回收，以免 Redis 故障期间放大压力。
27. **国际化。** 所有新增界面文案覆盖当前 Base 支持的 `en`、`zh`、`zh-TW`、`fr`、`ru`、`ja`、`vi`，并进入静态翻译键检查；不迁移二开中当前 Base 不支持的语言集合。
28. **架构记录。** 负载快照只提供候选排序与管理侧状态展示所需的观察结果、权威槽位获取决定所有权的安全边界遵循已接受的 ADR 0005；实施不得引入与该决策冲突的本地配额或槽位缓存。

## Testing Decisions

1. 测试只断言外部可观察行为、权限契约、持久化结果、Redis 命令预算和用户界面状态，不绑定私有函数拆分、组件内部 state、具体缓存容器或无业务意义的 DOM 结构。
2. 快照接口优先在完整 HTTP 路由与权限中间件接缝测试，而不只直接调用处理器：覆盖 `ChannelRead` 允许、缺权拒绝、访问令牌 scope 声明、空 ID、混合合法与非法 ID、超过 200 个片段、缺失渠道、无限制渠道跳过、完整返回字段，以及管理轮询与路由读取共享同一有界负载快照预算。
3. 渠道更新在真实 HTTP 更新接缝和临时数据库上测试：正数设置、显式 `0` 清除、字段缺失保持、`null` 保持、负数拒绝、新增渠道负数拒绝，以及更新后渠道缓存和重新读取结果一致。测试需覆盖 SQLite、MySQL 与 PostgreSQL 兼容的更新表达方式，不能依赖单一数据库的零值行为。
4. 渠道并发策略测试覆盖 12 项默认值、上限与非法值回退、热更新快照隔离、等待人数 `0` 自动跟随、主开关优先级、HTTP 429 开关、模糊消息开关、额度与余额错误排除、缓存关闭和抢占预算默认值。
5. 渠道并发服务沿用现有 Redis／内存双运行时测试接缝，并扩展固定基线中的 miniredis 与命令观测先例：验证重复读取命中缓存时不追加 Redis 抓取、并发未命中被 singleflight 合并、新鲜读取独立合并并刷新缓存、缓存关闭时每次读取、返回快照互不共享可变状态。
6. Redis 抗压行为测试覆盖超过 50 个渠道的分批读取且不丢候选、一次抓取只获取一次 Redis 时间、共享抓取最多 2 个并发槽位、3 秒边界、调用方取消不终止共享抓取、抓取饱和或失败时降级到进程内排序。
7. 权威获取测试覆盖并发冷却检查与槽位获取单次原子往返、同一请求续租、到达渠道并发上限后拒绝、无限制渠道的负载读取与槽位获取零 Redis 路径、权威 Redis 错误失败关闭、不确定结果只清理一次以及槽位租约最终释放。
8. 等待与选择测试覆盖原子等待登记不会在并发突发时越过上限、超时或释放后等待计数恢复、抖动落在规定区间、指数退避封顶、普通与 readiness 排名路径共享抢占预算、预算耗尽后选择最佳等待候选、低优先级候选不因分批或预算而从候选查询中消失。
9. 并发冷却选择测试覆盖缓存状态过滤所有候选后只进行一次新鲜确认、刚恢复渠道重新可选、新鲜确认失败保持软失败，以及明确 HTTP 429 与模糊关键词开关的所有组合。
10. 渠道表格组件测试使用受控接口响应、假时钟和页面可见性事件：验证立即请求、精确 10 秒间隔、当前页受限 ID 集合、标签子渠道、无限制渠道零请求、后台暂停、恢复刷新、查询集合隔离和卸载停止。
11. 渠道表格失败测试分别模拟网络异常、非成功 HTTP 状态和 `success: false`：首次失败显示 `-`，成功后任一失败保留最后快照，失败不产生轮询 toast，下一次成功可以正常更新。
12. 状态展示测试覆盖桌面表格与默认桌面卡片中的灰／黄／红 `active/max`、仅正等待数显示 `+N`、蓝色 `Cooling`、无限制渠道无快照、标签汇总行 `-`、移动表格与移动卡片隐藏以及明暗主题可读性。
13. 权限与行内编辑组件测试覆盖 `ChannelRead` 只读展示、`ChannelWrite` 可编辑、缺少 `ChannelRead` 不发起可用请求、正数提交、`0` 提交、负数前端阻止、成功后刷新以及服务端失败保留原配置。前端测试不能替代服务端授权测试。
14. 运维设置面板组件测试覆盖 12 项全部出现、常用／高级分组、默认值、数值范围、等待／并发冷却／缓存依赖禁用但保值、单渠道最大等待数 `0` 说明、无修改不请求、只保存变化项和稳定顺序逐项保存。
15. 设置部分失败测试模拟中间 Option 更新失败：失败项之后不再提交，之前成功项不回滚，不显示整体成功；重新加载后表单以服务端实际值为准。
16. 国际化验证覆盖七种现有语言的新增键、静态键清单、变量插值和无缺失回退；重点检查 `Cooling`、12 项设置名称、误判风险说明、`0` 自动跟随说明和权限受限状态。
17. 前端质量门覆盖受影响的 Vitest 测试、TypeScript 类型检查、lint、格式检查和生产构建；后端质量门覆盖受影响 Go 包的定向测试、竞态敏感并发测试，并在可承受范围内运行更广回归。
18. Playwright 使用真实当前 Base 管理界面完成桌面与移动验收：验证快照徽标、等待与并发冷却状态、移动隐藏、首次失败和失败保留、`ChannelRead` 只读、`ChannelWrite` 行内设置与 `0` 清除、Root 的 12 项设置实际保存与刷新持久化。动态状态使用受控测试状态或浏览器网络夹具，不调用真实上游模型。
19. 浏览器验收会记录临时配置的原值并在结束时恢复渠道并发上限和 12 项全局设置；测试失败也必须执行恢复，避免把验收数据留在开发环境。
20. 测试先例优先复用当前 Base 已有的渠道控制器权限测试、渠道字段更新测试、渠道表格组件测试、系统设置表单测试和真实浏览器验收方式，并吸收固定基线已有的渠道并发压力语义测试；不为同一行为创建重复的低层测试缝。

## Out of Scope

- 不创建独立渠道并发监控页面、Dashboard 卡片或新的顶级导航入口。
- 不持久化渠道并发快照，不提供历史曲线、时间序列、趋势、导出或回放。
- 不增加 QPS、吞吐、延迟、错误率、利用率图表、SLA、告警或通知。
- 不把渠道并发快照解释为渠道健康结论，也不改造现有渠道测试、自动禁用或健康策略。
- 不增加批量渠道并发上限编辑、标签汇总编辑或批量清零。
- 不改变现有专用批量接口及其 Codex 指纹相关能力。
- 不增加旧版本配置识别、数据回填、兼容默认值分支、迁移脚本或数据库 schema 迁移。
- 不缓存、预留或推测并发槽位所有权，不允许基于负载快照直接放行请求。
- 不改变渠道并发上限小于或等于零的无限制语义；其负载读取与槽位获取继续保持零 Redis 路径。既有错误反馈仍可按并发冷却策略写入冷却状态，本任务不额外改变该触发范围。
- 不重做全局重试策略、渠道分组、有效渠道策略、渠道亲和、模型健康或计费逻辑。
- 不迁移二开 Classic 前端，不整体合并二开目录，也不引入当前 Base 未支持的语言。
- 不在验收中调用真实上游模型或制造真实供应商费用。
- 本阶段不实现代码、不创建 ticket、不创建提交、不 push；后续阶段另行执行 `to-tickets` 与 implementation。
