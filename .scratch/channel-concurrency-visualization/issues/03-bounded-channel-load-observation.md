# 03: 有界的渠道负载观察

**What to build:** 平台请求调度器能以有界成本复用完整候选集的负载观察结果，在缓存陈旧、共享抓取拥塞或读取失败时保持既有选择语义和降级能力；全部 12 项后端渠道并发策略最终齐备并作用于运行时，而每个受限请求是否获准使用渠道仍只由权威槽位获取决定。

**Blocked by:** 02

**Status:** ready-for-agent

- [ ] 后端最终提供全部 12 项渠道并发策略，缺失值采用已确认默认值：等待开启、等待超时 `5000 ms`、单渠道最大等待数 `0`、并发冷却开启、冷却 `30 s`、HTTP 429 冷却开启、模糊消息冷却关闭、负载快照缓存开启、槽位 TTL `30 min`、等待轮询间隔 `100 ms`、缓存 TTL `200 ms`、每轮最大抢占次数 `8`；保存后的策略无需重启即可作用于后续请求。
- [ ] 负载快照缓存开关和 TTL 均真实控制运行时读取：开启时仅在有效 TTL 内复用结果，关闭时每次重新抓取；TTL 使用已确认默认值与有效边界，不会因零值、负数或越界值形成不一致状态。
- [ ] 缓存键同时包含稳定有序的候选渠道身份及各自渠道并发上限；候选身份、顺序归一化结果或上限变化会得到正确的缓存隔离，且每个调用方获得互不共享可变状态的独立快照。
- [ ] 候选集快照缓存的总条目数具有固定上限；高基数候选集持续进入时会淘汰旧条目而不是无界增长，淘汰只影响命中率与读取成本，不改变槽位所有权或候选完整性。
- [ ] 同一候选集的普通缓存未命中只触发一次共享抓取；绕过缓存的新鲜读取使用独立的合并范围，不与普通读取错误合并，并在成功后刷新可复用快照。
- [ ] 缓存中的并发冷却状态过滤全部候选时只执行一次新鲜确认；刚结束冷却的渠道可重新参与选择，新鲜确认失败保持原过滤结果并按软失败处理，不升级主请求错误。
- [ ] 完整候选集按稳定顺序分批读取，每批最多 50 个渠道，一次完整抓取只读取一次 Redis 时间；分批不截断候选、不丢失低优先级回退渠道，也不改变既有排序语义。
- [ ] 共享 Redis 负载抓取最多同时占用 2 个抓取槽位并受 `3 s` 总边界约束；共享抓取不受单个发起方取消支配，单个等待调用方取消只结束自身等待，不中止其他调用方仍在复用的抓取。
- [ ] 抓取槽位饱和、超时或负载读取失败时有界降级到既有进程内负载排序，不堆积无限后台工作；负载观察失败不会把权威 Redis 抢槽错误改为本地放行。
- [ ] 每次渠道选择共享同一抢占预算，默认最多对 8 个受限候选执行权威槽位获取，普通排序和 readiness 排名遵守同一预算；无限制渠道不消耗预算，预算耗尽后保留最佳等待候选并进入既有等待流程，不截断候选查询。
- [ ] 自动化测试证明陈旧负载快照只能影响候选尝试顺序：即使快照仍显示可用容量，并发请求也必须逐一通过实时权威槽位获取，不能突破渠道并发上限、制造未经确认的槽位租约或把快照当作可消费配额。
- [ ] 自动化测试覆盖缓存开关与 TTL、候选集缓存键、独立快照、缓存总容量与高基数淘汰、普通与新鲜读取合并、全冷却后的新鲜确认、50 渠道分批与单次 Redis 时间、2 个抓取槽位、3 秒边界、调用方取消、失败降级、默认 8 次抢占预算以及全部 12 项后端策略的默认值和热更新结果。
