## 二开一手核对结果

- 只读代理已核对固定树，未修改代码或运行测试。共同前提是性能采集开启且原始模型名非空，符合条件即记录，不是随机抽样。
- `pkg/perf_metrics/prometheus.go:81` 和 `pkg/perf_metrics/prometheus_model.go:266` 附近的最终模型指标包括：`newapi_model_requests_total{model,status}`、`newapi_model_request_duration_seconds{model,le}`、`newapi_model_ttft_seconds{model,le}`、`newapi_model_stream_success_total{model}`、`newapi_model_errors_total{model,error_category}`。其中 duration / TTFT 是包含 bucket / sum / count 的 histogram，耗时仅统计最终成功请求；TTFT 还要求成功流式请求具有有效首响应时间。
- 错误分类包含 `client_cancel`，不能直接把二开的全部最终错误计数当成 OP 的模型健康故障数；OP 对客户端主动取消采用忽略口径。正常结束、软错误等也必须核对实际终态，不能以 HTTP 200 或结算成功代替。
- 二开请求计数保留 6 小时；模型性能组默认最多 50 个，闲置 1 小时回收；默认每次 scrape 上限 5000 序列。非正配置会取消相应上限。默认与限制见固定树 `prometheus.go:14`、`prometheus_model.go:15`、`:343`。
- `newapi_model_histogram_active_models` 和 `newapi_model_histogram_dropped_samples_total{reason}` 是元监控，原因固定为 `model_limit/invalid_latency/invalid_ttft/series_limit`。基础指标优先，性能组按活跃度整组导出；预算不足时健康指标自身也可能不导出，基础序列超限可使抓取返回 500。
- `series_limit` 仅统计 latency / TTFT observation 的增量，不是所有请求和错误的完整丢弃计数。50 个性能组上限也不限制请求 counter 的全部模型数量，不能宣称整套指标全面有界且无损。
- 二开最终打点主要来自同步请求成功结算与最终失败边界，不是全入口请求账本；前置校验 / 预扣失败、异步任务终态和 Realtime 成功覆盖不对称。OP 既有请求 / WebSocket / 任务终态边界与之不同，后续需明确覆盖契约。
- TTFT 在通用流中可能是首个接受的非空 data 事件时间，不保证语义首文本 token；指标为进程内累计，不是持久账本。
- Grafana 和 GCP 的部署事实已在对话中核对；这些部署资产不等同于待补的应用指标契约。

- 术语修正：Responses WebSocket 不等于 Realtime。两树均有 `/v1/realtime`，但 OP 最终请求采样明确排除 Realtime；二开也没有完整的 Realtime 成功采样。因此不能把“保留 OP WebSocket 覆盖”说成已有完整 Realtime 统计。本轮没有因此决定新增 Realtime 全覆盖。证据：OP `controller/relay.go:193`；二开 `relay/websocket.go:44`、`controller/relay.go:255`。
- 普通 HTTP 主要是挂点不同：OP 请求边界采样，二开在文本 / 音频成功收尾与 controller 最终失败处采样；不因函数名不同就认定缺少普通请求统计。
- 治理边界已核对：OP `ClassifyRelayOutcome` 只由 `RecordRelayResult` 消费，禁用、冷却、重试及排除走独立错误治理链；统计对齐不要求保留旧分类兼容，也不自动改变这些业务行为。证据：OP `pkg/perf_metrics/metrics.go:33`、`controller/relay.go:264`、`service/relay_error.go:72`。
- ADR0006 不冲突：恢复中的首次拒绝不额外记一次最终失败，恢复结束仍按请求最终结果采样一次；不新增禁用 / 冷却动作。证据：OP `controller/relay.go:243`、`service/responses_encrypted_reasoning.go:70`。

### 后续补充：OP 新能力按需扩展监控

- 用户说明：`op如果有新的relay/其他新功能需要监控的，可以额外增加监控，不必强制对齐`。
- 确认原则：二开是共同观测能力的基线，不是 OP 的覆盖上限。除保留已存在的采样外，OP 新 relay / 其他新功能如有必要，可以补充采样或新增独立指标，按实际业务语义设计，不强制套用二开没有或不适用的实现。
- 接入共同请求指标 / 报表时仍采用已确认的二开口径，避免同一请求或任务终态重复累计；独立指标应明确统计对象与边界，控制标签基数，不暴露凭据等敏感信息。
- 该补充不恢复旧口径兼容、不要求处理测试环境历史、不改变不部署外部监控服务的决定，也不等于要求无差别重做所有功能监控。

## 访谈收敛
