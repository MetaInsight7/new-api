### Q5 投递可靠性边界

本期是否接受二开的尽力投递契约，而不扩展为可靠消息队列？例如机器人故障时本批消息不会自动补发，后续巡检仍失败才可能产生新告警；数据库冷却故障退回进程内时，也不保证跨副本去重。

推荐：本期按二开，不新增持久化待投递队列或应用级补发；投递失败可观测，但不改变测试结果、禁用或恢复判断。适配时仍保留 OP 的任务取消 / 租约边界，取消不能通过二开的独立后台 context 被绕开；已发出的消息无法撤回。

此前解释场景：10:00 渠道 A 测试失败，钉钉恰好超时，本批消息记录发送失败后被清空；10:10 A 若已恢复，不会补发 10:00 的旧消息，若仍失败且符合告警条件，才可能再尝试发送新告警。本题只讨论通知补发，不涉及 API 请求重试能力或再做一次渠道测试。

用户决定：`Q5按你的来`。采用本节推荐的尽力投递契约，不新增可靠消息队列或应用级补发，测试及治理判断保持原样，保留 OP 的取消 / 租约边界。

### Q6 与已有禁用通知的重复

同一次测试失败已经触发原有渠道禁用通知时，是否仍保留新增钉钉失败告警？二开没有把这两种通知合并。

推荐：对齐二开，两类事件均保留；原通知不改，新钉钉失败告警按自身冷却控制。本期不新增跨通知类型合并，也不把测试失败直接表述为禁用成功。

用户要求解释，尚未选择。场景：A 的测试失败命中现有自动禁用条件，且状态更新成功，原流程向管理员发送禁用通知；新增钉钉批次也报告 A 测试失败，同一故障可能出现于两种通知中。两种通知不保证发往同一接收位置，也不是渠道被测试两次；若未触发禁用，则不会因此产生原有禁用通知。OP 旧通知以状态更新成功为前提：`service/channel.go:37`。

用户此前继续追问：`Q6为啥会有两个通知，一个是newapi原始的？一个是二开的？`。核对答复：是，原有 New API 管理员渠道状态通知 + 二开新增定时测试失败钉钉告警；前者通知状态变化，后者报告测试失败，即使未禁用也可告警。不是默认向同一钉钉群重复发送两条，也不是我们额外新增两套测试。最终决定见下一段。

用户最终决定：`$to-spec 没问题`。确认上述说明和按二开保留两类通知的推荐，结束访谈并生成 spec；不删除原有官方状态通知，不做跨类型通知合并。
