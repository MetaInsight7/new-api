# 分组渠道策略覆盖 Spec

## Problem Statement

Base 当前只有渠道级别的全局优先级和权重。同一个模型在不同用户分组下只能使用同一套渠道排序和随机权重，无法让不同用户分组使用不同的渠道策略。

Overlay 已经具备按用户分组覆盖渠道优先级和权重的能力，但其实现不能直接覆盖到 Base：Base 的候选渠道、缓存、请求策略、并发调度和前端组件已经发生变化；Overlay 的权重覆盖路径还存在没有完全使用分组权重的缺陷。

同时，Base 新增的插件模式主要扩展厂商任务路由和协议适配，并不提供在渠道选择前修改候选渠道的安全接口。因此该能力需要作为 Base 核心路由能力迁移，而不是作为任务插件实现。

## Solution

为每个渠道增加可选的分组渠道策略覆盖。覆盖以 Base 现有用户分组为键，可独立覆盖 `priority` 或 `weight`；未覆盖的字段继承渠道全局值。

真实请求先沿用 Base 现有逻辑确定用户分组。普通分组直接使用该分组的有效渠道策略；`auto` 分组先按既有 `auto` 分组顺序解析出实际分组，再使用实际分组的有效渠道策略。分组覆盖不改变 `auto` 分组顺序。

主动模型探测仍然保存模型级可用性状态。探测顺序按渠道全局优先级降序、全局权重降序、渠道 ID 升序排列；分组覆盖不参与探测顺序，也不产生分组维度的探测状态。

管理员通过 Base 原生渠道编辑抽屉的可视化界面配置覆盖，并在渠道列表中看到已配置覆盖的分组提示。底层可以继续使用 JSON/text 保存，但管理员不需要直接编辑 JSON。

## User Stories

1. 作为管理员，我希望为一个渠道配置某个用户分组的优先级覆盖，以便该分组请求优先使用不同的渠道。
2. 作为管理员，我希望为一个渠道配置某个用户分组的权重覆盖，以便同优先级渠道之间按该分组的比例分流。
3. 作为管理员，我希望只覆盖优先级或只覆盖权重，以便未调整的参数继续沿用渠道全局值。
4. 作为管理员，我希望没有覆盖的分组继续使用全局优先级和权重，以便旧渠道行为保持不变。
5. 作为管理员，我希望删除某个分组覆盖后自动恢复全局值，以便撤销策略不会留下隐式状态。
6. 作为管理员，我希望在渠道编辑界面看到当前已配置的覆盖分组，以便不用读取原始 JSON 就能理解路由配置。
7. 作为管理员，我希望在渠道列表的优先级和权重附近看到覆盖提示，以便快速定位有特殊路由策略的渠道。
8. 作为管理员，我希望新建渠道时也能配置分组覆盖，以便新渠道可以直接加入既有分组策略。
9. 作为管理员，我希望编辑已有渠道时保留现有覆盖配置，以便普通字段编辑不会丢失路由策略。
10. 作为 API 用户，我希望普通用户分组请求使用自己分组的有效渠道策略，以便不同分组获得预期的渠道质量或成本分配。
11. 作为 API 用户，我希望 `auto` 分组仍按 API Key 中既有的分组顺序选择分组，以便分组覆盖不会改变现有分组选择语义。
12. 作为 API 用户，我希望 `auto` 分组确定实际分组后使用该分组的渠道覆盖，以便自动选择与渠道策略能够组合工作。
13. 作为 API 用户，我希望同一有效优先级内的渠道继续按权重随机选择，以便既有的容量分流能力保持可用。
14. 作为 API 用户，我希望上游失败重试时先耗尽当前有效优先级，再降级到下一个有效优先级，以便优先渠道失败后仍能可靠切换。
15. 作为 API 用户，我希望渠道健康过滤、并发限制和请求策略继续生效，以便分组覆盖不会绕过现有安全和容量控制。
16. 作为管理员，我希望主动模型探测仍按渠道全局优先级顺序执行，以便探测成本和顺序可预测。
17. 作为管理员，我希望即使每个用户分组都配置了覆盖，主动探测仍有明确的排序依据，以便不会出现“没有全局优先级”的探测歧义。
18. 作为管理员，我希望主动探测仍产生模型级可用性状态，以便 Available Models 和模型阻断不被迫改成分组维度。
19. 作为系统维护者，我希望旧渠道没有覆盖时不需要数据迁移或手工补配置，以便升级过程安全。
20. 作为系统维护者，我希望非法覆盖配置回退到全局值，以便单条错误配置不会让整个模型路由不可用。
21. 作为系统维护者，我希望未知分组覆盖可以保留但不参与路由，以便删除或重命名分组时不会静默丢失配置。
22. 作为管理员，我希望负优先级仍可使用，以便保留 Base 当前优先级表达能力。
23. 作为管理员，我希望负权重不能保存或参与随机选择，以便权重计算不会产生无效结果。
24. 作为系统维护者，我希望所有支持 Base 渠道选择的协议共用同一套有效策略，以便不会出现文本请求和任务请求行为不一致。
25. 作为开发者，我希望该能力不依赖插件运行时，以便每次渠道选择不增加 JavaScript 调用和插件失败风险。
26. 作为开发者，我希望分组策略计算在一个清晰的核心 seam 中测试，以便后续 Base 更新时可以局部解决冲突。

## Implementation Decisions

- 采用 Base 核心路由实现，不扩展当前插件 API。插件仍负责厂商任务路由和协议适配，不参与渠道候选选择。
- 保留渠道现有全局优先级和权重字段。它们既是未配置覆盖时的回退值，也是主动模型探测的排序依据。
- 增加可选的分组覆盖持久化字段。旧记录没有该字段时行为与当前 Base 完全一致。
- 覆盖字段以用户分组名称为键，优先级和权重可以独立存在。未配置的字段逐项继承全局值。
- 使用请求已经解析出的实际用户分组计算有效渠道策略。`auto` 分组顺序仍由现有 API Key 配置决定，不由渠道覆盖反向修改。
- 将有效渠道策略作为候选渠道选择的统一输入，覆盖真实请求的优先级层级、同层权重随机和重试降级；不绕过现有健康过滤、并发限制、渠道亲和性和请求策略。
- 复用 Base 当前渠道缓存和候选渠道结构，不直接覆盖 Overlay 的旧缓存实现；所有读取权重的路径都必须使用分组有效权重。
- 主动模型探测按模型保存状态，不保存分组状态。探测目标按全局优先级降序、全局权重降序、渠道 ID 升序排列；探测成功后可提前结束当前模型，全部失败后沿用既有错误分类和汇总规则。
- 前端采用 Base 原生的可视化分组覆盖编辑区，并在渠道列表中用紧凑提示显示覆盖分组；不要求管理员手写 JSON，也不复制 Overlay 的组件结构。
- 编辑器显示全局值的作用说明：它是未配置分组的回退值，也是主动探测排序值。
- 第一版只支持单渠道创建和编辑，不新增分组覆盖的批量或标签批量编辑，避免大范围误改路由策略。
- 非法 JSON、未知字段或运行时无法解析的覆盖回退全局值并记录可诊断日志；负优先级允许，负权重拒绝保存并在运行时安全回退。
- 未知分组配置保留在持久化数据中但不参与当前请求，避免分组删除或重命名导致配置静默丢失。
- 复用现有渠道管理权限、请求 payload 扩展方式、缓存重建和多数据库迁移约定，不引入新的公开路由。

## Testing Decisions

- 最高测试 seam 是“给定渠道、用户分组和候选请求条件，得到有效优先级/权重并选择渠道”的核心路由行为；测试通过公开行为验证，不断言缓存内部 map 排列。
- 覆盖未配置分组、只覆盖优先级、只覆盖权重、完整覆盖、非法 JSON、未知分组和旧数据无字段等行为。
- 覆盖正负优先级、零权重、负权重拒绝、同优先级权重随机和权重溢出保护等边界。
- 覆盖普通分组与 `auto` 分组，验证 `auto` 顺序不被覆盖配置改变，解析后的实际分组会使用对应覆盖。
- 覆盖优先级降级、渠道健康过滤、并发过滤、渠道亲和性和非普通 Relay 选择路径，确保策略不会绕过现有限制。
- 覆盖主动探测按全局优先级/权重排序，不读取用户分组覆盖；验证模型状态仍按模型维度保存。
- 覆盖 SQLite、MySQL 和 PostgreSQL 能接受新字段，旧记录加载后保持原行为。
- 后端测试优先复用现有渠道候选、缓存和调度测试 fixture；新增测试只断言路由结果、错误分类和持久化契约。
- 前端测试从管理员行为出发，验证添加分组、修改字段、删除覆盖、继承全局值、非法输入提示和已配置标签显示；不使用大范围 class 快照。
- 前端执行受影响 Vitest、TypeScript 类型检查、受影响文件 lint 和格式检查；关键渠道编辑流程使用 Playwright 验证。
- 提交前执行受影响 Go 测试以及完整的前端定向验证；不以生产构建替代行为测试。

## Out of Scope

- 不把该功能实现为插件，不新增通用路由策略插件 API。
- 不引入 PLG 独立可用分组、定价分组或充值分组。
- 不改变 Base 的用户分组与渠道分组领域语义。
- 不保存模型加用户分组维度的主动探测状态。
- 不为不同用户分组建立独立的 Available Models 页面模型状态。
- 不支持第一版的分组覆盖批量编辑或标签批量编辑。
- 不改变渠道健康状态、阻断状态、计费、模型倍率、供应商或协议展示。
- 不迁移 Overlay 的品牌、供应商、营销或其他未确认功能。

## Further Notes

- Overlay 的分组权重读取存在不完整路径，迁移时必须检查所有随机选择调用，不能只增加模型方法。
- 当前 Base 的核心路由实现比 Overlay 更新，Base 的请求策略、并发控制、任务插件和非普通 Relay 适配优先级高于 Overlay 旧代码。
- 全局优先级和权重在配置界面中不能被隐藏；它们仍是未配置分组的回退值和主动探测顺序依据。
- 该功能的 ADR 记录了“核心路由而不是插件”以及“探测与真实请求分离”的长期架构决策。
