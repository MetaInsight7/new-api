## Q3：来源的永久失效规则

本项按来源的人工确认规则迁移。以下是审计事实，不表示这些能力已实现：

- `ChannelStatusBanned = 4`，表示运维确认上游账号已被封禁或永久不可用。
- 管理员通过渠道更新接口标记该状态；它不参与路由。
- `UpdateChannelStatus` 是自动状态处理路径：目标状态为 `4` 时拒绝写入，当前状态为 `4` 时拒绝覆盖；多 Key 自动处理同样保护这一状态。
- 自动禁用使用状态 `3`。错误是否触发自动禁用仍取决于自动禁用开关、状态码和错误规则，不是任意 `401/429/5xx` 都固定触发。
- `ShouldEnableChannel` 只允许成功探测后的 `3 -> 1`；长时间连续失败不会升级为 `4`。
- Codex 自动凭证刷新只扫描状态 `1/3`，不扫描 `4`。
- 前端行操作提供“标记为已封禁”和“解除封禁”，后者通过管理接口写回状态 `1`。
- 原版的按标签批量启用也是人工管理路径，`EnableChannelByTag` 未排除状态 `4`。因此原版保证的是自动任务不能解封，不能把它描述为所有管理路径都只能使用单独的解除封禁按钮。
- 状态 `4` 是所有渠道共用的状态，不只针对 Codex。来源设计主要面向 Codex/GPT 账号池，但前端封禁行操作、状态筛选以及后端自动状态保护都没有 Codex 类型限制；不能把本次 Codex 配套迁移范围误认为来源功能仅适用于 Codex。

本轮采用来源的人工确认规则，不增加错误次数或时间阈值自动判定永久封禁。通用渠道前端按钮和显式人工批量启用行为保持来源语义，不擅自增加仅 Codex 限制或改变人工批量管理行为。

### 自动禁用（状态 3）的触发条件

来源澄清：状态 `3` 的通用自动禁用／自动恢复机制是官方 New API 自带能力，不是二开新增的 Codex 专属机制。核对官方 `main`（`56758edf9`）与来源最终代码，`ShouldDisableChannel`、`ShouldEnableChannel` 和默认自动禁用状态码规则保持相同的判断逻辑。二开新增的是状态 `4` 及其人工管理、筛选和自动状态覆盖保护。

迁移保留 Base 的状态 `3` 实现，不为 Codex 重造一套自动禁用，也不使用二开旧版覆盖官方已有的 WebSocket 关闭等较新处理；新增状态 `4` 时适配已有状态更新边界。

以下为来源固定基线的规则和源码默认值，不代表开发环境数据库中当前保存的配置：

- 普通 Relay 请求与渠道测试路径需要全局自动禁用开关开启，且该渠道 `AutoBan=1`。全局开关源码默认关闭。
- `ShouldDisableChannel` 先判断 `channel:` 前缀的渠道错误，包括无可用 Key、无效 Key、模型映射失败、参数或 Header 覆盖配置错误等。
- 对非渠道错误，带有 `skipRetry` 标记的错误不触发这一自动禁用判断；其余错误可由配置的 HTTP 状态码或错误关键词命中。
- 默认自动禁用状态码范围只有 `401`；`403/429/5xx` 不单凭状态码默认禁用，但仍可能命中关键词或管理员扩展的状态码配置。
- 默认关键词包括上游余额不足、组织禁用、配额超限、权限拒绝、无效安全令牌、不允许操作和账号未获授权的英文错误消息。
- 允许禁用的批量／定时渠道测试还会检查耗时；超过 `ChannelDisableThreshold` 可以禁用，源码默认阈值为 5 秒。这不是每个普通请求都执行的慢请求禁用规则。
- 普通自动禁用规则不要求连续失败次数；一次符合条件的错误或测试超时阈值即可触发。普通请求向 Relay 返回成功时不进入错误处理；不能把其他渠道重试后的整体成功误认为原失败渠道不会被禁用。
- 一渠道一账号的 Codex 场景会暂停整条渠道的全部模型，而不是只禁用报错模型；其他渠道不受该状态变更连带影响。
- 另外，支持余额查询的渠道在批量余额更新返回非正余额时会直接进入自动禁用路径，并检查渠道 `AutoBan`。该特殊入口没有复用全局错误判断；Codex 不支持此余额查询入口，不能把它当作 Codex 的额度禁用规则。

- 保持来源的通用渠道状态 `4`、人工确认和人工管理语义。
- 治理功能沿用来源默认关闭；不自动开启主动探测、外部公告抓取或 AI 判定。
