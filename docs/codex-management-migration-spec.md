# Codex 配套功能完整对齐规格

> 状态：已授权实施，先完成审计与 ticket 拆分，再逐项实现。
> 日期：2026-10-07。
> 目标：`new-api` 的 `tokendazi_op`，起点 `3eb021c5b`。
> 来源：二开最新版 `remotes/solve/main`，固定基线 `762ce21c4`。
> 官方对照：`main` 的 `56758edf9`；不能把迁移分支当成官方基线。

## Problem Statement

上一批已经迁移 Codex Relay 的八项能力，但尚未覆盖二开最新版的完整配套管理功能。用户需要迁移后能完成账号授权、渠道生命周期管理、额度观察、额度重置和模型生命周期审核，而不是只具备请求转发能力。部分已有功能由官方提供或比二开更完善，需要按实际行为对齐，不能覆盖较新的 Base 实现，也不能因只看个别提交而漏掉完整前后端链路。

## Solution

以来源最终代码为行为参照，在当前分支补齐 Codex OAuth、通用永久失效状态、Codex Limits、Codex Model Governance 和账号用量／重置细节。保持二开的入口划分：渠道页管理账号和凭证，Dashboard 汇总额度，独立治理页处理模型生命周期。继续保留已完成 Relay、R2、Identity、模型健康和分组调度能力，复用当前项目的授权、协议、组件和后台任务边界。

## User Stories

1. 作为管理员，我希望在新建 Codex 渠道时打开上游授权页面，以便不再手工构造凭证。
2. 作为管理员，我希望复制授权链接，以便浏览器拦截新窗口时仍能完成授权。
3. 作为管理员，我希望粘贴回调地址后生成 JSON 凭证并填入渠道表单，以便按正常保存流程创建渠道。
4. 作为管理员，我希望为已有 Codex 渠道重新授权，以便替换过期或撤销的凭证。
5. 作为管理员，我希望授权使用渠道配置的代理，以便与上游网络访问方式一致。
6. 作为管理员，我希望过期、跨会话、错配渠道或已用过的授权不能完成，以便防止凭证误绑定和重放。
7. 作为受限管理员，我希望敏感授权入口尊重我的渠道权限，以便不越权获得或更改凭证。
8. 作为管理员，我希望授权失败只显示可诊断但不含凭证的错误，以便保护账号。
9. 作为管理员，我希望标记确认永久失效的渠道，以便它不再被系统恢复。
10. 作为管理员，我希望在所有渠道类型的行菜单都能标记永久失效，以便保持来源的通用设计。
11. 作为管理员，我希望筛选已封禁渠道并查看徽标，以便区分临时禁用和永久失效。
12. 作为管理员，我希望显式解除封禁，以便纠正判断或在上游解封后恢复渠道。
13. 作为管理员，我希望自动测试和凭证刷新不改写永久失效状态，以便保持人工决定。
14. 作为管理员，我希望原有自动禁用规则不变，以便沿用官方已有配置。
15. 作为管理员，我希望查看所有 Codex 渠道的额度汇总，以便发现将耗尽的账号。
16. 作为管理员，我希望查看各账号实际提供的额度窗口，以便不把不存在的周／小时额度当成零。
17. 作为管理员，我希望查看重置时间、套餐和附加模型限额，以便判断账号可服务的范围。
18. 作为管理员，我希望查看查询失败原因，以便将上游异常与零额度区分。
19. 作为管理员，我希望额度报表同时展示所选时间范围的真实调用和用量，以便观察利用情况。
20. 作为管理员，我希望跨渠道查询具有有界并发和超时，以便不拖垮控制台。
21. 作为普通用户，我希望看不到上游账号额度和凭证管理，以便维持租户隔离。
22. 作为管理员，我希望在单渠道用量弹窗查看重置次数并确认消费，以便恢复上游额度窗口。
23. 作为管理员，我希望重置超时或认证失败时不自动重复消费，以便避免重复扣掉重置次数。
24. 作为管理员，我希望重置失败后的反馈与实际刷新结果一致，以便不把刷新失败误认为消费失败。
25. 作为管理员，我希望看到明确不支持的 Codex 模型发现，以便处理账号与模型的兼容性变化。
26. 作为管理员，我希望启用可配置的主动治理探测，以便在真实用户失败前发现不支持模型。
27. 作为管理员，我希望配置公告来源和生命周期判定规则，以便识别上游下线通知。
28. 作为管理员，我希望 AI／公告产生的推断需要审核，以便不凭不确定信息自动移除模型。
29. 作为管理员，我希望查看发现来源、受影响渠道、错误证据和审核历史，以便做出可靠决策。
30. 作为管理员，我希望禁用、恢复、忽略或确认移除模型并填写备注，以便完成治理闭环。
31. 作为管理员，我希望治理禁用只影响对应渠道模型能力，以便不误伤其他上游。
32. 作为管理员，我希望已有健康探测、渠道编辑或能力修复不能无意解除治理禁用，以便保持审核结果。
33. 作为管理员，我希望治理告警跨节点去重并保留冷却，以便避免重复通知。
34. 作为维护者，我希望新增治理数据可在 SQLite、MySQL、PostgreSQL 启动和升级，以便不限制部署数据库。
35. 作为维护者，我希望每项功能单独提交、附有真实测试结果，以便后续维护和回退。
36. 作为维护者，我希望已有 Codex 文本、图片、计费和身份功能不回退，以便完整对齐不是重新造轮子。

## Implementation Decisions

- 只以来源最终代码和当前 Base 实现比较完整行为，不直接合并整个二开分支，不迁移无关产品功能。
- 保留上一批八项 Relay 迁移；遗漏的 Codex 专属行为经审计后纳入独立补齐项，不回退 Base 的协议转换、WebSocket、安全、计费和缓存修复。
- 通用自动禁用状态 `3` 是官方已有能力，不重新实现。新增状态 `4` 保持来源人工标记语义，不按错误次数或失败时间自动判封。
- 状态 `4` 适用于所有渠道类型；操作使用当前渠道操作授权与专用状态接口，原有值 `1/2/3` 不变；多 Key 不新增子状态，同账号不自动连带封禁。
- 自动状态处理不得创建或覆盖状态 `4`；显式人工状态管理仍可修改它，保持来源的人工批量操作语义。状态更新继续同步能力、缓存、跨节点通知和 WebSocket 生命周期。
- OAuth 复用当前上游客户端 Identity 与代理网络层，以及 Base 持久化 AuthFlow。授权状态绑定管理员、会话及目标渠道，使用 PKCE S256、固定授权服务与回调契约、十分钟有效期和原子单次消费。
- 不复制来源未检查有效期、忽略 session 保存错误和仅成功后清理授权状态的缺陷。新建渠道生成凭证回填表单；已有渠道的凭证更换保留当前敏感写授权、审计与缓存失效。
- OAuth 管理接口必须有服务端敏感写权限、会话绑定、限流与禁止缓存；不能用前端隐藏代替授权。权限撤销、会话撤销、state 不匹配和重放必须失败。
- Codex Limits 是管理员 Dashboard 区块，使用当前渠道只读权限；详情不向普通用户暴露。报表保存成功／失败边界、真实窗口和时间范围统计，不伪造缺失数据。
- 跨渠道用量读取有界并发、统一超时；只读查询可在明确认证失败时刷新凭证后重试一次，缓存失效批处理，不改变计费热路径。
- Reset Credits 保留已有界面和独立查询能力，补齐来源的消费失败保护；同次消费因明确 `401/403` 刷新后重试时复用同一个 `redeem_request_id`，不对网络超时或不确定响应重新生成 ID 自动消费。不能宣称这种单次调用保护等于跨请求／跨标签页全局幂等。
- Model Governance 复用来源领域与最终 UI，适配当前后台调度、模型测试和能力层，不替代当前全局模型健康状态。对应渠道模型的治理抑制与健康恢复分别维护。
- 治理开关和主动探测默认关闭，探测默认周期、规则、连续明确不支持门槛和告警冷却按来源。普通超时、限流和网络失败不能被当作永久模型下线。
- 公告／AI 发现只进入待审核路径；外部来源访问使用现有 SSRF 防护、体积和超时限制；不增加默认外部来源，不偷偷开启 AI 调用。
- 治理记录、探测状态和告警冷却采用持久化数据，并沿用多节点任务和通知边界；不得用单节点内存状态替代需要跨节点一致的决定。
- 能力重建、渠道编辑、自动恢复和人工恢复需要保留有效的治理抑制；确认移除、恢复和忽略按来源范围执行，并保留审核人与备注。
- 新增表／字段仅做向后兼容迁移，使用当前跨数据库锁和保留字段引用规则，不复制不兼容 SQLite 的行锁写法。
- 前端复用现有 Dialog、ConfirmDialog、SectionPageLayout、Dashboard registry、格式化和日期／语言工具；保留当前已修复的账号详情，不用旧来源覆盖较新的组件。
- 所有新增用户文案支持项目语言体系；错误、空数组、未知窗口、缺失套餐及失败渠道必须可展示，不出现空白页面或 console 异常。

## Testing Decisions

- 优先在管理 API 的权限、OAuth 授权闭环、渠道状态流转、报表聚合和治理审核闭环测试真实行为，不为每个机械 helper 建独立测试层。
- OAuth 覆盖 PKCE、state、固定回调、过期、重放、跨会话／跨渠道、权限与凭证保存；仅模拟上游 HTTP 网络，不模拟被测业务流程。
- 状态测试覆盖 `4` 不可被自动创建或覆盖、状态筛选、显式恢复、能力与缓存同步、已有状态 `3` 不回退。
- 报表覆盖多账号部分失败、免费账号窗口、未知／附加窗口、统计口径、刷新后一次重试及边界超时；重置测试覆盖认证重试复用 ID、不确定失败不重试和刷新反馈。
- 治理覆盖明确不支持与普通错误分类、渠道模型抑制、编辑／重建保持抑制、审核恢复范围、连续探测证据、默认关闭与告警去重。
- 数据库涉及的行为在真实 SQLite、MySQL、PostgreSQL 测试；新增结构验证全新与既有结构升级，重复迁移至少两次，并核对数据、索引和唯一约束。
- 每项前端能力执行相关单测、类型检查、改动文件 lint 和 Playwright；Playwright 覆盖桌面／窄屏、导航、按钮与弹窗交互、权限、失败／空数据和 console 错误。
- 不向真实上游执行 OAuth 登录或消耗真实 Reset Credit 来“测试”；通过可控上游验证协议，部署后实际账号冒烟由拥有者执行。
- 最终执行 Codex 相关完整回归和生产构建；前端限制 CPU／线程／内存使用，避免再次使 VPS 无响应。未通过或未执行项必须如实记录，不能把文档勾选当作验证。
- 安全参照 OWASP Authentication、Session Management、OAuth 2.0、CSRF Cheat Sheets 与 ASVS 稳定版；记录采用的控制和验证，不声称未经证明的全面合规。

## Out of Scope

- 无关的品牌、供应商、PLG、钱包、订阅和营销重构。
- 新建统一 Codex 账号中心、独立账号表或同账号自动连带封禁。
- 自动判定账号永久封禁，以及批量转换既有账号状态。
- 以二开旧版取代较新的 Base Relay、计费或通用模型健康功能。
- 切回 GCS、迁移作者部署凭证，或公开上传任何临时媒体。
- 在未配置时启用治理探测、公告抓取或 AI 外部请求。

## Further Notes

- 已完成的 Relay 功能及其提交继续以 `docs/codex-channel-migration-spec.md` 和对应 ticket 记录为准，本规格是补齐批次，不改写之前完成记录。
- 来源的封禁设计声明“显式解除”，但人工按标签启用实际可覆盖该状态；本轮按真实代码语义描述，不宣称只有一个按钮能改变它。
- 按仓库 issue 治理规则，Codex 反代类工作不提交 GitHub issue；spec 和独立 tickets 保留在本地仓库，避免绕过项目规则。
- 运行时的全局自动禁用规则来自数据库设置，源码默认值不是当前环境配置。
