# 激活漏斗与用量报表完整迁移规格

## Problem Statement

`tokendazi_op` 已经迁移了激活漏斗、运营日报和用量报表的主体代码，但当前实现还不是新版二开 `new-api-solve/main` 的完整功能：

- 运营日报的“注册用户”表已经展示广告系列、落地页、IP、语言、支付国家等列，但 Base 没有迁移这些数据的持久化和采集链路，导致列长期显示为空；
- `ops-report` 当前缺少新版二开页面中的 Stripe 支付转化和广告日报入口；这两个
  外部数据源当前未启用，但仍需要以默认关闭的方式保留，避免将来重复开发；
- 用量报表主体已经具备 UTC+0 聚合、模型维度、异步回填、当前日刷新和 CSV 导出，但仍需要完成空数据、错误状态和真实浏览器行为验收；
- 之前的规格把归因数据错误地列为后续功能，造成“页面有列、数据无来源”的不完整迁移。

本规格以 `new-api-solve/main` 当前基线（审计时为 `762ce21c429a3aa9adc104bcd80eb7df3ad3bdbd`）为功能参考，**不以 Overlay 为实现基线**。代码必须适配 `tokendazi_op` 的 Base 用户、支付、订阅和认证模型，不整体合并二开仓库。

## Solution

完成两个管理员报表页面的端到端功能，而不是只复制页面组件。

### 1. 运营日报 / 激活漏斗

- 保留现有注册、激活、DAU、充值/订阅转化、周漏斗和付费用户明细；
- 补齐用户明细所需的数据来源：广告归因、浏览器语言、最近登录 IP、支付国家；
- 保留新版二开的注册用户明细列和付费用户明细列；
- 保留新版二开 `ops-report` 页面中的 Stripe 支付转化功能；Stripe 未配置时默认隐藏入口，接口不访问外部服务；
- 保留新版二开 `ops-report` 页面中的广告日报功能；广告平台未配置时默认隐藏入口，接口不触发同步；
- Stripe 和广告平台为可选外部数据源，配置后才显示入口并启用同步；暂时不可用时只显示明确的不可用状态，不阻断核心漏斗；
- Base 没有 Overlay 的独立 PLG 运营分组，DAU 继续统计普通客户用户，不增加伪造的 PLG/all 切换。

### 2. 用量报表

- 保留现有 UTC+0 自然日注册、当天激活、当天首付、调用次数、Prompt/Completion Token 和模型聚合；
- 保留历史日期异步幂等回填、当前日定时刷新和 CSV 导出；
- 补齐或验证空数据、回填中、回填失败、接口失败、CSV 下载失败等用户可见状态；
- 不改变请求、日志写入、余额或计费热路径。

## User Stories

### 运营日报与激活漏斗

1. 作为管理员，我想查看指定时间范围内的注册人数，以便了解用户增长规模。
2. 作为管理员，我想按广告系列、关键词和落地页查看注册分布，以便判断营销入口的效果。
3. 作为管理员，我想查看真实激活、真实 Playground 使用、人工 API Key 创建和 API Key 使用，以便区分有效用户与自动开户行为。
4. 作为管理员，我想查看 DAU、请求数和消耗趋势，以便了解激活后的真实使用情况。
5. 作为管理员，我想区分充值、订阅、首付和复购，以便判断不同付费路径的转化。
6. 作为管理员，我想查看注册用户的注册方式、IP、IP 国家、浏览器语言和支付国家，以便分析用户地域和异常转化。
7. 作为管理员，我想查看付费用户的余额、用量、最近活跃时间、主要模型和付费来源，以便定位高价值用户。
8. 作为管理员，我想在启用 Stripe 后查看 Checkout 创建、完成、失败和支付方式国家，以便诊断支付转化问题。
9. 作为管理员，我想在启用广告平台后查看广告关键词、创意、落地页、成本、点击和变更，以便每天运营广告投放。
10. 作为管理员，我想在 Stripe 或广告平台没有配置时仍能查看核心漏斗，且不产生外部请求或后台同步任务。
11. 作为管理员，我想在查询失败时看到错误状态，而不是把失败误显示为零值。
12. 作为管理员，我想知道运营日报采用的日期和时区口径，以便不误解统计结果。

### 用量报表

13. 作为管理员，我想查看 UTC+0 每日注册人数，以便与调用趋势使用同一日期维度比较。
14. 作为管理员，我想查看注册用户当天首次创建 API Key 的人数，以便衡量用量激活。
15. 作为管理员，我想查看每日调用次数、Prompt Token 和 Completion Token，以便估算产品使用规模。
16. 作为管理员，我想按模型查看调用和 Token 消耗，以便了解模型偏好和成本结构。
17. 作为管理员，我想查看模型在日期范围内的排行、占比和趋势，以便识别主要使用模型。
18. 作为管理员，我想选择不同的日期范围，以便比较短期趋势和长期趋势。
19. 作为管理员，我想导出每日汇总和日期×模型明细 CSV，以便进行外部分析。
20. 作为管理员，我想在历史回填、部分数据、刷新失败和接口失败时看到准确状态，以便判断数据是否完整。
21. 作为管理员，我想保证打开用量报表不会改变在线请求、余额、计费或消费日志写入行为。
22. 作为普通用户，我不能访问两个管理员报表及其数据接口。

## Implementation Decisions

### Baseline and domain adaptation

- `new-api-solve/main` 是功能基线；Overlay 只作为历史背景，不作为代码来源。
- `tokendazi_op` 的 `users.role` 是报表客户群边界；不把 Base 的模型路由/定价 `group` 解释成 Overlay 的 PLG 营销分组。
- 管理员报表接口继续使用服务端管理员鉴权；前端路由保护不替代后端鉴权。
- 钱包和订阅管理页面不迁移；运营报表可以读取现有充值和订阅事实，并保留充值/订阅来源拆分。

### User acquisition and payer identity data

- `users` 增加 `ads_attribution`、`browser_lang`、`last_login_ip`、`pay_country` 四个分析字段，空值对既有数据兼容。
- 广告归因以受限 JSON 保存，只接收允许的 UTM、广告点击 ID、Campaign、Keyword、落地页、Referrer、语言等字段；服务端重新清洗，不能信任浏览器传入的任意 JSON。
- 前端在根路由捕获首次落地 URL、广告参数、搜索来源和 Referrer，使用现有浏览器存储机制跨页面保存；密码注册和 OAuth 注册都提交同一归因载荷。
- OAuth 归因必须进入服务端 OAuth 流程状态并在回调创建用户时恢复，不能依赖回调页面的可控参数或绕过现有 CSRF/一次性状态校验。
- 登录时从服务端请求的 `Accept-Language` 和 `ClientIP()` 更新最近一次浏览器语言与控制台登录 IP；这是分析字段，不改变授权判断。
- Stripe 成功支付后从支付方式/银行卡发卡国家写入 `pay_country`；读取失败不得阻塞支付入账，需记录可诊断日志并允许后续重试/回填。
- 报表优先使用支付国家，其次使用控制台登录 IP 的 IP 地理解析；不使用 API 请求 IP 或 webhook 服务器 IP 代表用户所在地。

### Ops report optional boards

- 核心运营日报、Stripe 转化和广告日报使用独立接口及缓存，外部 API 请求不能阻塞核心漏斗。
- Stripe 转化只在进入 tab 时懒加载，服务端负责 Stripe API 调用、用户映射、时间范围、结果上限和缓存，前端不接触 Stripe 密钥。
- 广告日报使用新版二开的按日同步/快照模型，保存关键词、创意、落地页和变更摘要；没有广告配置时接口返回 `configured=false` 或明确错误状态。
- 广告日报只统计配置允许的品牌广告数据，不把其他业务线的共享广告账户数据混入核心漏斗。
- 外部数据的“不可用”与“无数据”必须区分，不能用空数组掩盖凭证、网络或 API 错误。

### Usage report

- 用量报表继续使用独立的按日和日期×模型聚合表，不修改消费日志写入链路。
- Base 没有新版二开的邮箱验证时间字段，注册口径使用普通用户、启用状态和创建时间；不能为了复制 SQL 引入不存在的列。
- 付费金额沿用 Base 已有 `top_ups` 与订阅镜像事实，不重复计算同一笔订单。
- 历史日期按 UTC+0 日期幂等重算；当天按固定间隔刷新；后台回填错误通过 API 状态传递到前端。
- 聚合失败返回明确错误，不把失败转换成正常的零值；报表读取失败不得影响线上请求和计费。

### Commit boundaries

- 用户归因、登录信息、支付国家及运营日报明细数据链路作为一个独立功能提交。
- Stripe 支付转化 tab 作为一个独立功能提交。
- 广告日报及其同步/快照作为一个独立功能提交。
- 用量报表空状态、错误状态和回归测试作为一个独立功能提交；如果审计后确认没有代码缺口，只提交验证记录，不伪造改动。
- 最终 Playwright、定向测试、Lint、类型检查和完整测试作为验收提交，不与功能实现混淆。

## Testing Decisions

- 后端测试以外部行为为主，覆盖字段清洗、密码注册归因、OAuth 状态归因、登录语言/IP更新、Stripe 支付国家失败降级、运营报表明细和管理员鉴权。
- 运营日报测试覆盖普通用户边界、注册/激活/付费口径、充值与订阅拆分、归因解析、IP 国家优先级、Stripe/广告外部数据不可用状态。
- 用量报表测试覆盖 UTC 日期边界、Base 用户口径、模型聚合、回填幂等、当前日刷新、错误状态和 CSV 内容。
- 前端测试覆盖报表加载、空状态、部分回填、错误提示、日期切换、CSV 下载、可选外部 tab 的不可用状态和可访问名称。
- 涉及前端改动必须使用 Playwright 验证真实管理员页面、日期切换、注册用户明细和可选报表 tab；普通用户必须验证导航隐藏和路由拒绝。
- 使用项目现有 Go 测试、Vitest/React Testing Library 和路由测试模式；测试不绑定私有实现细节。
- 验证顺序为受影响后端测试、前端定向测试、类型检查、Lint、资源可控的前端构建、Playwright，最后再运行完整测试。

## Out of Scope

- 不迁移 Overlay 的旧报表口径、旧布局或 PLG 分组语义。
- 不迁移新版二开的 Ads Pilot、官网营销落地页、邮件召回、钱包/订阅管理页面和其他运营系统；本次只实现 `ops-report` 页面中的核心、Stripe 转化和广告日报 tab。
- 不新增支付方式、不重构钱包或订阅结算逻辑；只读取已有业务事实并在成功支付后写入分析字段。
- 不把广告或 Stripe 外部 API 变成核心注册/激活漏斗的硬依赖。
- 不把分析字段用于授权、分组、倍率、渠道调度或计费。
- 不改变 Relay、请求日志、余额扣减和计费热路径。

## Further Notes

- 旧用户的注册、调用、充值和订阅数据可以从既有表恢复；广告归因通常无法从历史数据可靠恢复。
- 浏览器语言和最近登录 IP 从功能上线后的下一次登录开始记录；支付国家从成功支付或可验证的历史 Stripe 订单回填。
- `ops-report` 使用现有运营日报日期口径（US Pacific），`usage-report` 使用 UTC+0；两个页面必须持续显示各自口径。
- 新增四个用户字段后，数据库迁移必须支持 SQLite、MySQL 和 PostgreSQL，并保证旧行默认为空字符串而不是迁移失败。
