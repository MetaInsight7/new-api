# 激活漏斗与用量报表迁移规格

## Problem Statement

当前 `tokendazi_op` 已具备用户、充值、钱包和订阅等业务领域，但还没有迁移新版二开中的两套管理员分析能力：

- 运营人员无法在控制台统一查看注册来源、用户激活、使用和付费转化；
- 管理员无法按日期和模型查看调用次数、Token 消耗及模型使用趋势；
- Overlay 中的报表实现已经过时，直接复用会把旧的指标口径、缓存策略和页面设计带入新分支；
- 如果把运营转化与模型用量做成同一个耦合报表，后续指标口径和性能优化会互相影响。

本规格以 `new-api-solve/main` 的最终实现为功能参考，不以 Overlay 为实现基线，也不将新版二开整体合并到 `tokendazi_op`。

## Solution

迁移两个相互独立、均只对管理员开放的报表模块：

1. **运营日报 / 激活漏斗**
   - 展示注册、注册来源、运营激活、DAU、充值与订阅转化；
   - 展示付费用户明细及充值/订阅来源拆分；
   - 保留新版二开的运营激活定义和最终页面交互；
   - 广告日报和 Stripe 专项审计作为独立后续功能，不混入本次核心激活漏斗迁移。
2. **用量报表**
   - 使用 UTC+0 自然日统计注册、用量激活、调用次数、Prompt/Completion Token；
   - 按模型聚合调用和 Token，并提供 CSV 导出；
   - 历史日期异步回填，当天数据周期性刷新；
   - 报表读取不修改请求和计费热路径。

两个模块可以展示部分相同事实，但必须保留各自的指标名称、日期口径和计算语义。

## User Stories

### 运营日报与激活漏斗

1. 作为管理员，我想查看指定时间范围内的注册人数，以便了解用户增长规模。
2. 作为管理员，我想按注册来源、Campaign 和 Keyword 查看注册分布，以便判断不同营销入口的效果。
3. 作为管理员，我想查看完成运营激活的用户数，以便判断注册用户是否真正开始使用产品。
4. 作为管理员，我想查看激活率随时间的变化，以便发现注册到使用之间的转化问题。
5. 作为管理员，我想查看 API Key 创建、API Key 使用和真实 Playground 使用等激活行为，以便区分主动使用与自动开户行为。
6. 作为管理员，我想查看 DAU、请求数和消耗趋势，以便了解激活后的真实使用情况。
7. 作为管理员，我想查看充值成功、订阅成功、首付和复购等付费阶段，以便分析激活到付费的转化。
8. 作为管理员，我想区分充值和订阅的订单数与金额，以便判断不同商业化路径的贡献。
9. 作为管理员，我想查看付费用户明细，以便定位高价值用户和异常转化记录。
10. 作为管理员，我想在数据查询失败时看到明确的错误状态，而不是把缺失数据显示为正常的零值。
11. 作为管理员，我想在没有配置广告平台时仍能使用核心注册和激活漏斗，以便外部营销服务不是报表的硬依赖。
12. 作为管理员，我想在不同报表使用不同日期口径时看到明确的时区标识，以便避免错误比较数据。

### 用量报表

13. 作为管理员，我想查看 UTC+0 每日注册人数，以便与用量趋势进行同一日期维度的比较。
14. 作为管理员，我想查看注册用户在规定窗口内首次创建 API Key 的人数，以便衡量用量激活。
15. 作为管理员，我想查看每日调用次数、Prompt Token 和 Completion Token，以便估算产品使用规模。
16. 作为管理员，我想按模型查看调用和 Token 消耗，以便了解模型偏好和成本结构。
17. 作为管理员，我想查看模型在每日和选定区间内的占比与排行，以便识别主要使用模型。
18. 作为管理员，我想选择不同的日期范围，以便比较短期趋势和长期趋势。
19. 作为管理员，我想导出每日汇总数据，以便在外部表格中进行进一步分析。
20. 作为管理员，我想导出按日期和模型拆分的数据，以便结合外部价格计算成本。
21. 作为管理员，我想在历史数据首次请求时看到回填状态，以便知道页面数据是否仍在生成。
22. 作为管理员，我想在当天数据刷新失败时保留已生成的历史数据，并得到明确提示。
23. 作为管理员，我想保证打开报表不会改变在线请求、计费或日志写入行为，以便报表查询不会影响用户请求。
24. 作为管理员，我想在无权限时无法访问两个报表及其数据接口，以便保护其他用户的使用和付费信息。

## Implementation Decisions

### 来源与架构

- `new-api-solve/main` 是两个模块的唯一功能参考基线；Overlay 只用于历史理解，不复制其旧逻辑。
- 代码适配 `tokendazi_op` 的现有领域模型、认证、路由、前端组件和数据库约定，不做整分支合并。
- 运营日报和用量报表保持独立的接口、聚合逻辑、页面状态和数据表，不通过一个共享的大型报表对象耦合。
- 两个模块均使用管理员权限保护；普通用户不能看到其他用户的转化、用量或付费数据。

### 运营激活漏斗

- 运营激活表示用户完成可证明其主动使用产品的行为，包括主动创建或使用 API Key、CLI Key 或真实 Playground 使用；自动发放 Key 和自动触发请求不应伪装成主动激活。
- 运营日报保留注册来源归因、运营激活、DAU、充值/订阅转化和付费用户明细。
- 运营日报统计 Base 的普通用户账号，不按 `User.Group` 过滤，也不引入 Overlay 的
  `group='plg'` 运营人群语义；管理员账号排除，禁用账号由管理员开关决定是否纳入。
- Base 当前没有 Overlay 新版的广告归因、浏览器语言、登录 IP 和支付卡国家字段；运营日报保留这些脱敏字段和页面列，但在字段迁移单独批准前按空值返回，不伪造数据。
- 充值和订阅计入统一付费转化，但必须保留订单数、金额和来源拆分。
- 广告日报与 Stripe 专项分析不属于本次核心迁移；如果核心报表需要外部广告或 Stripe 数据，应以可选数据源处理，不能阻塞无外部配置时的核心漏斗。
- 运营日报沿用新版二开的日期口径，并在页面和文档中标识时区。

### 用量报表

- 用量报表使用 UTC+0 自然日。
- 用量激活表示注册 cohort 在规定时间窗口内完成首次建 Key 的人数；页面不得把它简称为与运营激活完全等价的“激活”。
- 用量事实包含调用次数、Prompt Token、Completion Token 和按模型聚合的调用/Token 数据。
- 历史日期采用按日幂等聚合并落库的方式，首次读取可以触发异步历史回填。
- 当天数据按固定刷新间隔重新计算；高频读取不重复执行完整历史聚合。
- 支持每日维度和日期×模型维度的 CSV 导出。
- 报表聚合失败不能改变用户余额、计费结果、请求处理或日志写入；接口应返回可识别的错误或回填状态，不用零值掩盖失败。

### 前端与交互

- 两个页面以新版二开的最终布局、图表、交互和字段为准。
- 只适配 Base 当前组件、路由、权限、国际化和订阅/充值数据结构，不回退到 Overlay 的旧布局。
- 页面必须明确显示运营日报与用量报表的日期口径。
- 历史回填、当天刷新、部分数据和下载失败都要有可见状态。

### 数据与接口

- 为用量日报及日期×模型明细建立独立的聚合存储，不改造现有消费日志写入链路。
- 聚合任务必须按日期范围查询并具备幂等重算能力，避免每次打开页面扫描全部历史日志。
- 充值和订阅数据沿用 `tokendazi_op` 已有业务事实，不另造一套支付账本。
- 接口只返回报表所需的脱敏统计和管理员明细，不返回渠道密钥或其他敏感配置。

### Commit 边界

- 激活漏斗作为一个完整功能提交，包含其后端、前端、测试和文档。
- 用量报表作为一个完整功能提交，包含其后端、前端、测试和文档。
- 如果两个功能确实需要共享的报表基础能力，则先单独提交该基础能力，再提交两个功能；不能把两个功能混成一个无法独立回滚的提交。

## Testing Decisions

- 测试以外部行为为主，不绑定内部函数或缓存实现细节。
- 运营日报后端测试覆盖：注册 cohort、运营激活去重、自动 Key 排除、充值与订阅拆分、付费汇总、来源归因、DAU、日期边界、无外部广告配置和管理员鉴权。
- 用量报表后端测试覆盖：UTC 日期边界、注册与用量激活口径、调用/Token 按模型聚合、历史回填状态、当天刷新、幂等重算、CSV 内容、聚合失败不影响业务写入和管理员鉴权。
- 前端测试覆盖：页面路由权限、日期范围、时区提示、图表/表格空状态、部分回填状态、充值/订阅拆分、下载按钮和错误提示。
- 使用项目现有 Go 测试、前端单元/组件测试和路由测试模式；页面完成后使用 Playwright 验证真实管理员页面。
- 验证顺序从受影响的后端定向测试和前端定向测试开始，再执行相关包类型检查、Lint 和完整测试；前端构建使用资源可控方式。

## Out of Scope

- 不以 Overlay 代码作为实现基线。
- 不把运营日报和用量报表合并为一个页面或一个聚合接口。
- 不迁移广告日报和 Stripe 专项审计页面；后续可单独立项。
- 不新增或重构钱包、充值、订阅领域；只消费 `tokendazi_op` 已有业务事实。
- 不修改请求、计费、余额或消费日志热路径来写入报表计数。
- 不接入新的 GA、Mixpanel 或其他外部分析平台；本次报表以服务端可审计数据为准。
- 不迁移品牌官网、供应商业务或 Overlay 的 PLG 专属分组语义。

## Further Notes

- 两个报表都可能出现“注册”和“付费”等相同字段，但由于激活定义和日期口径不同，页面不得直接暗示它们可以逐列相除或相互替代。
- 新版二开中的异步回填和当前日刷新是性能要求，不是可选的实现细节。
- 报表应支持在无历史聚合表数据的线上环境中平滑创建和回填，首次回填期间不影响正常业务。
